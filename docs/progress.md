## Stage 0C Part 2B — recommendation response contract (2026-11-27)

**Problem and why it mattered.** An **API contract** is the agreed shape, types, status codes, and meaning of requests and responses. The similar-movie route returned a plain dictionary without a declared response model, so OpenAPI did not describe its successful payload and FastAPI did not validate it on return. The Streamlit page and external clients already consume specific fields; documenting and validating those fields makes accidental server-side changes easier to detect. This also gives a future AI tool or agent a discoverable, typed result to consume.

**Before-and-after wire contract.** Before modifying the route, two new isolated API tests passed against its existing output and errors. The **200 JSON is unchanged**: `{ "movie_id": int, "title": str, "recommendations": [{ "movie_id": int, "title": str, "genres": str | null, "similarity": float }] }`. `recommendations` may be empty; `genres` is always a key and may be JSON `null`; similarity is rounded to four decimal places by the existing service; recommendations preserve model order and omit IDs with no movie metadata. A trained model plus missing movie returns `404 {"detail":"Movie not found"}`; an unavailable/untrained model returns `503 {"detail":"Recommendation model is not ready"}`; invalid `k` outside 1–20 returns 422 with a validation-detail list. These status codes and messages were verified before and after the change. The model-readiness check precedes the movie lookup as before.

**How the change works.** **Pydantic** defines and checks the shape of data entering or leaving an API. `SimilarMovieItem` requires `movie_id`, `title`, `genres`, and `similarity`; `genres: str | None` accepts a present `null` but does not silently omit the field. `SimilarMoviesResponse` requires the seed `movie_id`, `title`, and a list of those items. FastAPI's `response_model` validates the service's returned dictionary and serializes it to JSON. A mismatched server result raises `ResponseValidationError` and, without a custom handler, is an internal server error rather than a client-input 422. A targeted test deliberately omits `genres` to verify that guard. **SQLAlchemy models** represent database tables and queries; Pydantic models describe HTTP data contracts. A separate `app/schemas/recommendation.py` follows the existing domain-based schema layout and avoids mixing recommendation scores into the catalogue `movie.py` schema. Extending `movie.py` was possible but would conflate distinct responses. No new dependency or framework was added.

**Files changed for Part 2B.** Added `app/schemas/recommendation.py`; updated `app/api/recommendations.py` to declare `response_model=SimilarMoviesResponse`; added `tests/test_recommendation_api.py` for exact JSON, empty/nullable results, 404/503/422 errors, generated OpenAPI references and required fields, and invalid service output. Updated this progress record plus `ARCHITECTURE_OVERVIEW.md`, `TECHNICAL_DEBT.md`, `REFACTORING_ROADMAP.md`, and `FILE_USAGE_AUDIT.md` to reflect current behavior. Existing service logic, frontend code, SQLAlchemy models, database schema, and recommendation algorithms were not changed. Earlier uncommitted Stage 0C work remains in the same working tree.

## Stage 0C Part 2D — health, readiness, and startup reliability (2026-11-27)

**Problem and observed baseline.** `/health` always returned `200 {"status":"healthy","application":"MovieVerse"}` even when the model or database was unavailable. FastAPI lifespan read every rating and trained KNN before accepting traffic; an unavailable database, no ratings, or model training failure each stopped startup. The recommendation route already returned 503 when the model was absent. No frontend code calls `/health`; an existing API test only checks that it returns 200. Database configuration creates a SQLAlchemy engine at import but usually opens a connection only on query.

**Policy and trade-offs.** Preserve `/health` exactly as process liveness. Add `/ready` for full database-plus-recommender readiness. A database query failure remains **fail-fast** because database-backed catalogue, watchlist, and analytics routes cannot work. Memory exhaustion during training also stops startup because the process may no longer be safe to serve. Empty ratings or ordinary model initialization failure now use **graceful degradation**: the API starts, catalogue routes work if the database works, recommendation requests return their existing 503, and `/ready` returns 503. This is an intentional startup policy change. A deployment that gates all traffic on `/ready` will also withhold working catalogue routes while the model is absent; a separate catalogue readiness contract can be considered later only with a concrete deployment need.

**Implementation.** `app/main.py` clears stale recommender state before startup and on shutdown, reads ratings once, trains only when records exist, and catches model initialization failures with a generic warning that does not expose exception details. Startup database query failures still propagate; the session closes in `finally`. `/ready` runs a single `SELECT 1` through the existing `get_db` session, checks `is_trained`, and returns `200 {"status":"ready","database":"available","recommendation_model":"available"}` or 503 with `status: "not_ready"` and `available`/`unavailable` component values. It neither counts ratings nor retrains the model. Existing SQLAlchemy, FastAPI, pytest, SQLite, and fake recommender tools were sufficient. Alternatives were changing `/health`, failing startup for all model problems, or reporting readiness for catalogue alone; the chosen policy preserves the old wire contract and makes full recommendation readiness explicit.

**Verification.** `tests/test_health.py` added nine cases: unchanged liveness, ready database/model, database failure without leaked details, missing or untrained model, empty ratings, ordinary model training failure, memory exhaustion, and fail-fast database startup with session closure. Full isolated suite: **77 passed, 1 warning in 19.52 seconds**, compared with **68 passed, 1 warning** before Part 2D. The nine new cases account for the increase. No API/server startup latency or memory improvement was measured. `SELECT 1` is lightweight, but current connection settings do not guarantee a hard timeout if establishing a connection stalls.

**Learning and independent reproduction.** A **health endpoint** reports that the process can answer HTTP; a **readiness endpoint** reports whether required dependencies can serve the intended workload. **FastAPI lifespan** runs startup code before requests and cleanup after shutdown. **Fail-fast** stops startup when a required dependency fails; **graceful degradation** keeps usable features available when an optional component fails. ## Stage 1A — dataset manifest and source metadata (2026-11-27)

**Problem and scope.** `load_data.py` currently uses fixed `data/raw/movies.csv` and `data/raw/ratings.csv` paths. A **dataset manifest** is a small description of the exact input files. **Metadata** describes files rather than their individual rows; **data lineage** connects an output to the input files and processing steps that produced it. Stage 1A establishes input identity only; it does not attach a manifest to a database ingestion job.

**Implementation and tools.** `app/data_pipeline/manifest.py` uses standard-library `hashlib`, `csv`, `json`, and UTC `datetime`. It reads each file in 1 MiB binary chunks for SHA-256, parses CSV records without loading all rows, and records relative names, byte sizes, columns, and data-row counts. It rejects missing, zero-byte, header-only, duplicate/blank-header, malformed-width, invalid-encoding, and broken-quote files. A **checksum** is a compact value derived from content; **SHA-256** is the hash algorithm used here. The combined fingerprint hashes sorted file-name/checksum pairs, excluding generation time and descriptive metadata, so unchanged bytes keep the same fingerprint. `compare_manifests` reports added, removed, modified, and unchanged files. The CLI prints JSON by default; `--output` writes a new file and `--compare` reads a saved baseline. `.gitignore` excludes `data/manifests/`; no generated manifest was committed. **Counting policy.** For movies, a valid numeric `movieId` is the key; for ratings, the key is a valid numeric `(userId, movieId)` pair. The first such key in file order is the duplicate reference, even if that row has another error; later occurrences receive `duplicate_key`. Invalid keys are not grouped as duplicates. Each row's rejection masks are combined with logical OR, so **total = accepted + rejected** and a row with several errors counts once as rejected. Reason counts are separate and can sum above rejected rows. `invalid_data_type` means a nonnumeric value in a numeric field or a nontext movie title; that row may also appear under `invalid_id`, `invalid_rating`, or `invalid_title`. Missing-value counts are per actual column and are not automatically rejection counts: null movie `genres` are allowed by the existing row rule, but the `genres` column itself is required. If a required column is absent, every parsed row in that file is rejected under `missing_required_column`. Accepted and rejected percentages use total parsed rows as denominator; an empty in-memory frame reports `null` percentages, while the file manifest rejects header-only CSV input.
